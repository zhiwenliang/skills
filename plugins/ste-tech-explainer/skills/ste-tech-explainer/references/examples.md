# 示例与反例

这些是自编教学示例，用于选择解释粒度；不是正式 STE 合规模板。

## 条件与因果不能因短句丢失

原句：“只有系统显示导入成功时，才能查看本次结果。”

失真拆分：“查看结果。系统显示导入成功。” 条件被拆成了另一个事实，动作关系改变。

保真：“仅在系统显示‘导入成功’时，才可查看本次结果。” 短句内保留必要条件与许可语气。

不能改成“如果系统显示‘导入成功’，单击‘查看结果’”。后者没有保留未成功时不能查看的限制，还把许可改成了操作指令。

同样，“按住按钮，同时转动旋钮”不能改成“按住按钮。转动旋钮。” 后一种写法没有说明两个动作需要保持同时发生。

## 清晰不等于绝对化

不准确：“重试不会重复扣款。”

有边界的教学设定：“某服务用请求标识查找已保存的操作结果。如果首次结果已被可靠记录，且重试复用同一标识，服务直接返回已有结果。”

该例没有覆盖并发首次请求、记录过期和跨服务副作用，不能推出所有重试都只执行一次。真实实现仍需说明这些条件。不要为了通俗就写成无条件承诺。

## 最小示例必须有区分力

解释“同步与异步”时，只展示两个立即返回的函数，没有显示等待、控制权交还或结果获取，读者无法用例子区分机制。应选择一个需要等待的操作，并说明等待期间调用者能做什么。是否给代码取决于用户的目标。

解释相近概念时，先固定同一个场景和比较维度，再改变相关条件。不要同时替换场景、数据和目标，让读者无法判断差异来自哪里。

## 根据请求缩放

- “80 字内解释缓存”：保留定义、减少重复获取的原因、过期风险；省略图、自测与完整实现。
- “我会 Java，用实例解释 Rust 借用”：连接已有知识，但不把垃圾回收和借用检查视为同一机制；围绕一个访问冲突展开。
- “只问缓存穿透与击穿的区别”：围绕请求对象是否存在、热点项是否过期、后端压力来源比较；无需先介绍全部缓存架构。

这些是粒度示例，不规定必须出现的标题、用词或案例。
