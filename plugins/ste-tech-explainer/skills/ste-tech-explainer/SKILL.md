# 清晰技术解释

让读者能说清概念的含义、关键机制或形成原因、适用边界，并据此判断一个新例子。借鉴 ASD-STE100 的表达原则；中文教学建议不等同于正式英文 STE 规则，也不宣称文档符合该标准。

## 确定本次解释的范围

- 优先使用用户已给出的目的、背景、篇幅和格式要求。只回答所问层级；不要把单个概念扩成课程或多个文件。
- 背景未说明时，以具备一般计算机常识、未学过该概念的读者为默认。直接解释；仅在背景差异会改变答案时，简短说明假设或追问。
- 明确的“100 字内”“只解释区别”“不要代码”“不要练习”等要求优先。篇幅不足时，保留定义、主要因果与关键边界，省略装饰、延伸与自测。
- 发现错误前提时，先指出需要更正的具体判断，再解释原因。不要用更流畅的文字重复错误结论。
- 涉及版本、产品能力或具体实现时，查一手文档，固定版本和范围；不要把某产品行为写成通用定义。用户禁止联网时，遵守限制并说明重要的未核实处。

## 组织解释

以下是内容选择顺序，不是必须展示的标题模板。

1. 用一句话给出定义，直接回应问题。
2. 按概念类型说明相关问题、形成原因或引入目的。方案可以解释解决了什么；现象可以解释如何形成及其影响。读者已经熟悉的背景可省略。
3. 按依赖顺序解释机制。新术语先定义再使用；一次只推进读者理解当前机制所需的概念。
4. 给出最小但能区分关键机制的例子。交代初始状态、参与者、条件、动作和结果，并把结果联系回定义。
5. 指出会改变判断的边界、代价或易混概念。不要穷举周边知识；仅将必要的概念引入正文。

根据用户问题合并或省略步骤。极短答不添加教学仪式。较长解释中，把相关短句组成连贯段落；保持“因为—机制—结果”的推理链。

## 控制语言中的歧义

- 同一概念固定称呼。首次出现给出必要的中文定义与英文术语；别为避免重复而替换名称。不同概念不能因俗称相近就合并。
- 一句话尽量表达一个主要意思。允许必要的条件、因果从句；不按中文字符数机械切句，不照搬英文 20/25 词限制。
- 明确动作的执行者、对象和结果。指代可能对应多个对象时，重复对象名称。
- 必须先知道的条件放在动作前。保留“同时”“直到”“只有”等逻辑关系，不能把并行动作拆成先后动作。
- 改写时保留条件的方向与语气：“只有”不等于“如果”；“允许”不等于“必须执行”；“可能”不等于“必然”。条件不足时不要补成保证。
- 操作说明按执行顺序编号，每步通常一条指令；概念解释用自然段，只有并列或比较信息才用列表、表格。
- 保留“不一定”“在此实现中”“未核实”等有事实依据的限定。复核“只有”“一定”“都”等强判断：示例中的一种实现不能升级为概念的必要条件。准确性优先于句子短或语气肯定。
- 类比必须对应一个具体机制，并指出会误导读者的边界；类比不替代真实机制。

## 示例、代码与证据

- 自行构造的场景、数值和参数标为教学设定；不把缺失需求补成技术事实。
- 不为展示完整而添加代码。用户需要动手时，给出环境前提、最小代码、运行方式和预期结果。
- 能在合适的隔离环境中执行时，运行相关最小示例。分别标注实际观察与依据文档推演的预期结果；未执行就明确写“未运行”，不称“已验证”。
- 没有合适运行环境时，不擅自启动服务、连接生产系统或安装大批依赖。给出可复现步骤与验证限制。
- 对会影响结论的实现差异引用相邻的一手来源。引用具体章节或锚点前，确认该节直接支持相邻判断；仅同页或主题相关不够。不要为常识句堆砌链接，不编造来源，也不让参考资料列表替代证据。
- 图示仅在它能清楚表达关系、顺序或状态时使用；表格用于有相同比较维度的项目。
- 用户要求练习，或较长学习型解释确有巩固价值时，可加少量自测；答案分开。一般问答不默认添加测验。

## 交付前检查

在内部检查，不向读者输出固定清单：

- 是否回答了原问题，并遵守背景、长度与格式？
- 核心结果能否由前述条件和机制推出来？有没有把必要的并行、因果或范围限制删掉？
- 示例是否真正区分了概念？技术事实、教学设定与运行结果是否分清？
- 能否删掉一个无关概念、重复句或无帮助的图表，而不影响理解？

需要核对 STE 迁移边界或研究依据时，读 [原则与来源](references/principles-and-sources.md)。复杂解释失去连贯性，或需要确定例子粒度时，读 [示例与反例](references/examples.md)。不必每次加载参考文件。
